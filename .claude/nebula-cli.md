# Nebula Docs CLI — Architecture

The renderer + tooling. Pairs with the Platform documented in [nebula.md](nebula.md). For locked decisions and the SSR/auto-import gotchas, see [decisions.md](decisions.md). For current open work, see [status.md](status.md).

## TL;DR

`@nebula-docs/cli` is a multi-tenant Astro-based static site generator. Each tenant team has their own docs repo (`docs.json` + `theme.json` + `content/`), pulls in the CLI as a dev dep, and runs `nebula build` in CI. The CLI is invisible to editors — they edit in the Platform, the Platform commits to the tenant repo, CI builds and deploys.

**Stack:** Astro 5+ with `@astrojs/mdx`, `@astrojs/react`, Tailwind v4. Static-first. React components hydrate as islands; tenants who write pure prose ship zero JS.

**Binary:** `nebula`. Subcommands: `init`, `dev`, `build`, `preview`, `validate`, `upgrade`. `init` + `upgrade` are signature stubs today; the rest are functional.

**Distribution:** versioned npm package. Tenants pin in their `package.json` and upgrade when they choose.

## How multi-tenancy works

```
                       ┌──────────────────────┐
                       │   Platform (SPA)     │
                       │   Edits docs.json    │
                       │   + MDX via GH App   │
                       └──────────┬───────────┘
                                  │ commits
                                  ▼
            ┌──────────────────────────────────────────┐
            │           Tenant docs repos              │
            │   docs.json · theme.json · content/      │
            │   assets/ · components/ · package.json   │
            └────────┬─────────────────────────────────┘
                     │ CI runs `nebula build`
                     ▼
              ┌─────────────────────────┐
              │ Tenant deploy target    │
              │ Firebase Hosting        │
              └─────────────────────────┘
```

Each tenant **owns**: their docs repo, their GH App installation, their CI pipeline, their deploy target.

Each tenant **does NOT own**: the CLI (npm package), the component library, the base theme system, the Platform.

## Tenant repo layout

```
<tenant>-docs/
├── docs.json                     # The contract. Platform reads/writes this.
├── theme.json                    # Optional per-tenant theme overrides.
├── package.json                  # Pulls @nebula-docs/cli as a dev dep.
├── .github/workflows/deploy.yml  # Generated by `init`. Runs build → deploy.
│
├── content/
│   ├── index.mdx                 # Home.
│   ├── developers/...
│   └── snippets/                 # Reusable MDX fragments (not pages).
│
├── assets/                       # logos, images, favicon
├── components/                   # Optional: tenant-specific React components.
├── public/                       # Optional: passthrough static files.
└── nebula.config.ts              # Optional: programmatic escape hatch.
```

**Routes derive from `content/`.** `content/foo/bar.mdx` → `/foo/bar`. `index.mdx` is the folder root. No magic.

**`docs.json` controls navigation, branding, and platform behavior.** Not routing — routing comes from the file tree. This split matters: Platform edits `docs.json` to reorganize the sidebar; moving a file is a separate operation.

**`theme.json` is a JSON patch over a base theme.** Most tenants pick `"base": "uhc"` or `"base": "optum"` and stop.

**`components/` is auto-registered.** Any `.tsx` file here is available in MDX without explicit import. _Important: only auto-import React components, never Astro components — see [decisions.md](decisions.md) for the auto-import shadowing gotcha._

## The `docs.json` contract

The most load-bearing schema in the system. It's the contract between the Platform (produces it) and the CLI (consumes it). Designed to subset Mintlify's `docs.json` for editor familiarity, with additions for theme layering and analytics.

Key sections (full schema in `packages/schemas/src/docs/`):

- `name`, `description`, `favicon`, `logo` — identity
- `theme` → `{ base, extends, switcherEnabled, switcherOptions }` — theming
- `navigation.tabs[].groups[].pages[]` — nav tree (Mintlify-aligned; Tabs→Groups→Pages and Tabs→Menus→Groups/Pages are the only patterns in scope today)
- `navbar`, `footer` — chrome
- `search` → `{ provider: "pagefind", scopeBy: "tab" }` — Pagefind opt-in; omit to ship zero search JS
- `analytics` → `{ provider: "firebase" }` — opt-in; omit to ship zero analytics JS
- `redirects`, `errors.404` — routing extras

**Validation.** Tenants get a JSON Schema published at a stable URL. The CLI validates at build time; Platform validates on save.

## Build pipeline (what `nebula build` does)

1. **`resolveTenant`** — locates the tenant directory from the CLI arg, propagating `INIT_CWD` so relative paths work from the monorepo root.
2. **`prepareAstro`** — reads `docs.json` + `theme.json`, deep-merges over the base theme tokens, emits `.nebula/tokens.css` (via `@nebula-docs/theme`'s `generateTokensCss`). Also reads `docs.json.analytics` + root `.env` and emits `.nebula/analyticsConfig.mjs` (gitignored).
3. **Astro build** — file-routed pages via Astro 5 content collections. `src/content.config.ts` defines a `docs` collection globbing `**/*.mdx`. `src/pages/[...slug].astro` does `getStaticPaths` mapping `entry.id === 'index'` → `/`.
4. **MDX** — runs through `@nebula-docs/mdx`'s `remarkAutoComponentImports` (auto-import React-only components from the catalog) and `remarkBasePrefix` (rewrite hrefs/srcs under `NEBULA_BASE` for preview deploys).
5. **Layout chrome** — `DocsLayout.astro` + `Navbar`/`Sidebar`/`SidebarGroup`/`Footer` Astro components consume `docs.json`.
6. **Astro components** — for blocks that need to introspect children (Tabs, Steps, Mermaid, CodeGroup), the runtime uses `.astro` slot wrappers in `src/runtime/components/`. See the SSR boundary note in [decisions.md](decisions.md).
7. **Pagefind post-build** — `src/integration/searchIntegration.mjs` `astro:build:done` hook indexes `dist/` if `docs.json.search` is set.

## Preview-before-merge (`--base` flag)

`nebula build --base /previews/42` produces a bundle whose paths resolve under that prefix:

- **Layout chrome** — `withBase()` helper in `src/runtime/lib/nav.mjs` is the choke point for Sidebar/Navbar/Footer/breadcrumb hrefs. External / hash-only / scheme-relative URLs pass through.
- **MDX content** — `remarkBasePrefix` walks MDAST rewriting `link`/`image` URLs plus string-valued `href`/`src` on JSX flow/text elements. Idempotent, no-op when base is unset.
- **Expression-valued attrs** (`<Card href={someVar} />`) aren't rewritten — wrap with `withBase` yourself.

Preview URLs land on `builds/{run_id}.previewUrl` in Firestore via Firebase Hosting Preview Channels: the tenant workflow runs `firebase hosting:channel:deploy` (channel ID derived from branch name), extracts the channel URL from the CLI's JSON output, then POSTs it to the `recordPreview` Cloud Function with shared-secret auth. The dashboard subscription reads the doc and surfaces the Preview button.

## Snippets (Mintlify-aligned ES imports)

ES module imports, not a custom JSX wrapper:

```mdx
import Disclaimer from "/content/snippets/disclaimer.mdx";

<Disclaimer />
```

- **`@nebula-docs/mdx`** provides `extractImports`, `parseImportStatement`, `groupImportsByPath`, `serializeImports`, `extractExports`, `bindingNameFromPath`, and the `remarkAutoComponentImports` plugin.
- **Vite aliases** map `/snippets/*`, `/content/snippets/*`, `/shared/*` to the tenant root so absolute import paths work from inside MDX.
- **Editor side** tracks imports in `importsRef` parallel to `frontmatterRef`; serializer re-emits captured imports verbatim at the top of the body.
- **Editor catalog** walks both `<docsSubdirectory>/content/snippets/` and `<docsSubdirectory>/snippets/`, canonicalizing to a single `/snippets/...` import path.

## Components map

The page route in `src/pages/[...slug].astro` merges three sources:

1. **Core React blocks** from `@nebula-docs/components` (Callout, Card, Frame, ParamField, etc.).
2. **Astro shims** in `src/runtime/components/` for blocks that need to introspect children (`Tabs.astro`, `Steps.astro`, `Mermaid.astro`, `CodeGroup.astro`).
3. **Tenant-local components** from `<tenant>/components/*.tsx`.

Astro shims override React versions in the merge. _Astro components MUST NOT be auto-imported_ — the `remarkAutoComponentImports` plugin would shadow them with the React import. Keep them out of the auto-import map.
